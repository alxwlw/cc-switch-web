# Дизайн: cc-switch-web как самостоятельный OSS-продукт

**Status:** draft (2026-11-19)
**Ветка:** `feat-cld/oss-release` (worktree `.worktrees/oss-release`, от `origin/main@b43896c1`)

Пометки: **[владелец]** — решил владелец в разговоре; **[моё]** — решил автор дизайна, владелец может
переиграть; без пометки — факт из кода или прямое следствие решений.

## Зачем

Сейчас форк `alxwlw/cc-switch-web` снаружи выглядит как зеркало апстрима `farion1231/cc-switch`: README,
спонсоры, бейджи, `SECURITY.md`, `CODEOWNERS`, шаблоны issues и релизный workflow — апстримовские. Релизов
нет, образ нигде не публикуется, поставить можно только сборкой из исходников (`scripts/install-server.sh`
собирает pnpm + cargo) и только на хост с Tailscale. Пользоваться им может только владелец.

Цель — чтобы посторонний человек нашёл репозиторий, понял за первый экран, что это и зачем, поставил за пять
минут и дальше обновлялся без сборки.

## Для кого

**[владелец]** Человек с той же проблемой, что у владельца: агенты (Claude Code, Codex, Gemini CLI и
остальные, которыми управляет cc-switch) работают на удалённом Linux-сервере без десктопа. Десктопный
cc-switch там не запустить, поэтому провайдеров, MCP и skills он правит руками по SSH.

Догадки о нём (не проверены): уверенно работает с SSH и Docker, сам ставит сервисы на свой сервер;
не хочет собирать Rust и Node; Tailscale у него может не быть.

Отличие от соседних веб-форков (`zuoliangyu/cc-switch-web` — 24★, релиз v3.3.2 от 2026-11-11, то же имя и тот
же каталог данных `~/.cc-switch-web`; `xiaoY233/cc-switch-remote` — 14★, заброшен с августа): форк идёт за
свежим апстримом 4.0.x, держит паритет с десктопом (модуль web-parity M5 закрыт) и обновляет себя сам.

## Что считается готовым

1. Пуш тега `v<апстрим>-web.<N>` сам выпускает GitHub Release: бинарники linux x86_64 и arm64, `SHA256SUMS`,
   `install.sh`, и образ `ghcr.io/alxwlw/cc-switch-web` (amd64 + arm64).
2. На чистых Debian 12, Ubuntu 22.04 и Ubuntu 24.04 одна команда из README ставит сервис, а вторая (на
   ноутбуке) открывает консоль в браузере. В CI это проверяет smoke-тест в контейнерах этих дистрибутивов.
3. Тот же результат даёт путь через Docker Compose из README, и консоль видит конфиги агентов хоста.
4. Установка из релиза обновляет себя до следующего релиза из консоли (Settings → About), с откатом при
   неудаче. Проверено вручную на agentbox (там есть systemd user unit `cc-switch-web`, сейчас остановлен) на
   двух настоящих релизах: `-web.1` с новым механизмом обновления и следующий за ним. Пререлизы для этого не
   годятся: `releases/latest` их пропускает.
5. Первый экран README и все «собственные» файлы проекта (список ниже) описывают форк; ссылок на спонсоров
   апстрима, его бейджи и ccswitch.io в них нет.
6. Пробная синхронизация с текущим апстримом по новой процедуре не трогает собственные файлы форка и не
   даёт в них конфликтов.

## Не делаем

- Сборки под Windows и macOS: сервер — только Linux.
- Свою авторизацию, TLS, многопользовательский режим (вариант «токен в ссылке» отвергнут **[владелец]**).
- Десктопные сборки Tauri, их подпись и нотаризацию.
- Отвязку сервера от Tauri **[владелец]**: это 57 файлов апстримового кода с `tauri::` и вечные конфликты
  при синхронизации. Отдельный проект, если когда-нибудь понадобится.
- Переводы README **[владелец]** (позже), переименование проекта **[владелец]** (имя `cc-switch-web` остаётся).
- Переписывание апстримовской документации (`docs/user-manual/`, `docs/*-integration-zh.md`,
  `docs/release-notes/`): остаётся как есть, README на неё не опирается.
- Продвижение (посты, ссылки в апстриме): владелец сам, если захочет. Здесь — только описание и topics
  репозитория.
- Подпись артефактов (minisign/cosign, attestations) **[моё]**: в первой версии — только `SHA256SUMS`.

## Чего нельзя допустить

- **Синхронизация с апстримом превращается в ручную работу.** После этой работы README, `SECURITY.md`,
  `.github/` и т. п. становятся файлами форка, а апстрим правит их постоянно. Каждая синхронизация должна
  оставлять их нашими без ручного разрешения конфликтов (механизм — ниже, «Синхронизация»).
- **Сервис по умолчанию открыт наружу.** Без логина единственная защита — адрес, на котором он слушает.
  Ни установщик, ни compose-пример не должны по умолчанию открывать порт на внешнем интерфейсе.
- **Обновление ломает работающую установку без отката.**
- **Правки апстримового кода «по пути».** Код форка живёт за адаптерами (`src-tauri/src/web_api/`,
  `src-tauri/examples/server.rs`, `scripts/`, `src/lib/api/` и т. п.), как требует `docs/upstream.lock`.
  Версии в `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json` — апстримовские, форк их не
  меняет.

## Ограничения (факты из кода, `origin/main@b43896c1`)

- Сервер — `src-tauri/examples/server.rs`, слинкованный с `cc_switch_lib` и Tauri. `ldd` собранного бинарника
  показывает 128 библиотек, в том числе `libwebkit2gtk-4.1`, `libgtk-3`, GStreamer, X11, Wayland. Рантайм-
  пакеты Debian, которых хватает для запуска, перечислены в финальной стадии `Dockerfile.web`:
  `libssl3 libgtk-3-0 libayatana-appindicator3-1 librsvg2-2 libwebkit2gtk-4.1-0`.
- Сервер уже слушает `127.0.0.1:18766` по умолчанию (`HOST`, `PORT`) и отказывается слушать не-loopback
  адрес без `TRUSTED_TAILNET=1` (fail closed, `examples/server.rs:163`).
- Статику консоли (`dist-web`) он раздаёт из `WEB_DIST`; без неё отдаёт только `/api/*`.
- Commit сборки зашивается при компиляции через `CC_SWITCH_WEB_GIT_SHA` (`buildSha` в `/api/capabilities`).
- Проверка обновлений (`src-tauri/src/services/web_update.rs`) сравнивает этот commit с головой ветки через
  GitHub compare API, кеш на час. Самообновление (`src-tauri/src/web_api/self_update.rs` +
  `scripts/self-update.sh`) — только для systemd user unit, выключено по умолчанию
  (`CC_SWITCH_WEB_SELF_UPDATE=1` + `CC_SWITCH_WEB_SOURCE_DIR`), запускает скрипт в транзиентном юните
  `cc-switch-web-update`, который делает `git pull`, собирает, подменяет бинарник и `dist-web` с копиями
  `.prev`, перезапускает и откатывает при неудаче; прогресс — в `update-status.json`, консоль его показывает.
- `Dockerfile.web` собирается и работает (PR #40), но в CI не собирается.
- В `main` версия апстрима 4.0.20; ветка синхронизации `sync/upstream-6da70837` (в основном checkout, не
  слита) поднимает её до 4.0.35.
- В `.github/` всё апстримовское: `release.yml` (десктоп, подпись, нотаризация; триггер — тег `v*`),
  `sync-r2.yml`, `wsl2-nightly.yml`, `stale.yml`, `claude.yml`, `labeler.yml`, `ci.yml`; `CODEOWNERS`
  (`@farion1231`), `FUNDING.yml` (`github: farion1231`), шаблоны issues и PR.

## Как устроено

### 1. Версии

- Тег релиза — `v<апстрим>-web.<N>`, например `v4.0.35-web.1` **[моё, владелец согласился]**. `<апстрим>` —
  `version` из `src-tauri/Cargo.toml` на коммите тега; `<N>` растёт с 1 на каждый релиз форка поверх одной
  версии апстрима. Релизный workflow отказывает, если `<апстрим>` в теге не совпадает с `Cargo.toml`.
- Версия форка зашивается в бинарник при компиляции отдельной переменной (по образцу
  `CC_SWITCH_WEB_GIT_SHA`) и отдаётся в `/api/capabilities`; у сборки не из релиза она `null`. Консоль
  показывает её в Settings → About.
- Каждый тег публикует релиз, и все установки с самообновлением на него переходят. Поэтому тег ставит
  исполнитель, но только после явного «выпускай» владельца на каждый релиз **[владелец]**.
- `CHANGELOG.md` — свой, по разделу на релиз; тело GitHub Release берётся из раздела этого релиза. В начале
  файла — строка о том, что изменения апстрима смотреть в его CHANGELOG (ссылка).

### 2. Артефакты релиза

- `cc-switch-web-<версия>-linux-x86_64.tar.gz` и `…-linux-aarch64.tar.gz`: бинарник + `dist-web`.
  Собираются нативно на `ubuntu-22.04` и `ubuntu-22.04-arm` **[моё]**: glibc 2.35, поэтому бинарник
  запускается на Ubuntu 22.04+ и Debian 12+, а `libwebkit2gtk-4.1` в 22.04 есть.
- `SHA256SUMS` по обоим архивам.
- `install.sh` — тот же, что в репозитории, с зашитой версией своего релиза. Ссылка
  `https://github.com/alxwlw/cc-switch-web/releases/latest/download/install.sh` всегда ведёт на установщик
  последнего релиза.
- Образ `ghcr.io/alxwlw/cc-switch-web:<версия>` и `:latest`, multi-arch amd64 + arm64, из `Dockerfile.web`
  с commit и версией в build-args.

### 3. Установка бинарником (`install.sh`) **[владелец: путь A]**

Команда из README: `curl -fsSL https://github.com/alxwlw/cc-switch-web/releases/latest/download/install.sh | bash`.

Что делает:
1. Определяет архитектуру (x86_64 / aarch64; иначе — ошибка со ссылкой на Docker).
2. Скачивает архив своего релиза, проверяет по `SHA256SUMS`.
3. Проверяет, хватает ли системных библиотек (`ldd` по бинарнику, строки `not found`). Если не хватает и есть
   `apt-get` — один раз ставит пакеты из списка `Dockerfile.web` через `sudo` **[владелец: вариант 1]**,
   предупредив, сколько это займёт. Если `apt-get` нет — печатает недостающие библиотеки, советует Docker и
   выходит с ошибкой.
4. Раскладывает файлы **[моё]**: бинарник `~/.local/bin/cc-switch-web`, статика
   `~/.local/share/cc-switch-web/dist-web`, копия установщика рядом (для самообновления), unit
   `~/.config/systemd/user/cc-switch-web.service`, данные — `~/.cc-switch-web` (не трогает, если уже есть).
5. Пишет unit: по умолчанию `HOST=127.0.0.1`. С `--tailscale` — адрес `tailscale ip -4` и `TRUSTED_TAILNET=1`
   **[владелец: 1 + 2]**. `--port` меняет порт. Самообновление включено **[моё]**: установка из релиза
   обновляется только до опубликованного релиза; `--no-self-update` выключает.
6. `systemctl --user daemon-reload && systemctl --user enable --now cc-switch-web`, затем
   `loginctl enable-linger "$USER"`, чтобы сервис жил без открытой SSH-сессии (если не вышло — печатает
   команду, которую надо выполнить).
7. Ждёт `/api/health` и печатает: установленную версию; для loopback — готовую строку
   `ssh -L 18766:localhost:18766 <user>@<host>` и `http://localhost:18766`; для `--tailscale` — URL в
   tailnet; где лежат данные; как удалить.

Ещё:
- Повторный запуск — обновление или переустановка той же раскладки.
- `--uninstall` удаляет бинарник, статику, unit и копию установщика; данные оставляет.
- Без systemd user session (контейнер, WSL без systemd) — ставит файлы, печатает команду запуска в
  foreground, самообновление недоступно.
- `scripts/install-server.sh` (сборка из исходников) остаётся для контрибьюторов и описывается в
  `CONTRIBUTING.md`, не в первом экране README.

### 4. Установка через Docker **[владелец: путь B]**

- В репозитории — пример `compose.yml` (место — на усмотрение исполнителя), README даёт команду, которая
  работает копипастой.
- Контейнер работает от UID/GID пользователя хоста и монтирует его `$HOME` по тому же пути с тем же `HOME`
  **[моё]**: так он видит конфиги всех агентов (`~/.claude`, `~/.codex`, `~/.gemini`, …) и данные
  `~/.cc-switch-web`, а список папок не нужно поддерживать под каждый новый агент. Так уже работает
  развёртывание владельца в Dokploy.
- Сеть — `network_mode: host` **[моё]**, а адрес задаётся тем же `HOST`, что у `install.sh`: по умолчанию
  `127.0.0.1`, вариант для tailnet — адрес tailnet и `TRUSTED_TAILNET=1` (закомментированными строками).
  Причина: локальный прокси cc-switch слушает `127.0.0.1:15721` (`src-tauri/src/proxy/types.rs:45`), и
  takeover прописывает этот адрес в конфиги агентов хоста. В bridge-сети с одним опубликованным портом агенты
  хоста до прокси не достучатся, и включённый из консоли takeover их сломает. Сервер и так только под Linux,
  поэтому ограничение host-сети (только Linux) ничего не стоит. Значения по умолчанию в образе
  (`HOST=0.0.0.0`, `TRUSTED_TAILNET=1`) compose переопределяет.
- Самообновление в контейнере недоступно (нет systemd — уже так); консоль показывает
  `docker compose pull && docker compose up -d`.

### 5. Проверка обновлений и самообновление

- Если в бинарнике зашита версия форка: проверка сравнивает её с последним релизом
  (`GET /repos/{repo}/releases/latest`), статусы те же (`up-to-date` / `behind` / `unknown`), кеш и `?force=1`
  как сейчас; консоль показывает версию последнего релиза и ссылку на его заметки вместо списка коммитов.
- Если версии нет (сборка из исходников): остаётся нынешнее сравнение по коммитам **[моё]** — им пользуются
  контрибьюторы и, до переезда, сам владелец.
- Самообновление установки из релиза использует ту же механику, что сейчас: транзиентный юнит, тот же файл
  статуса, подмена с копиями `.prev`, перезапуск, проверка здоровья с ожидаемой версией, откат. Вместо
  `git pull` и сборки — скачивание архива нужного релиза и проверка по `SHA256SUMS`. Названия стадий для
  этого режима исполнитель выбирает сам; консоль должна их понимать.
- Подсказки ручного обновления в Settings → About: для установки из релиза — снова запустить команду
  установщика; для Docker — команды compose.

### 7. Синхронизация с апстримом

- В `docs/upstream.lock` появляется список собственных путей форка (README и переводы, `SECURITY.md`,
  `SUPPORT.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `CHANGELOG.md`, `LICENSE`, `.github/**`, `docs/deploy.md`
  и т. п.; итоговый список — исполнителю).
- Скрипт синхронизации (например `scripts/sync-upstream.sh`) делает шаги из `upstream.lock` и после merge
  возвращает собственные пути в состояние форка: изменённые — версия форка, удалённые форком — снова удалены;
  конфликтами остаются только настоящие, в коде.
- **[моё, отличается от сказанного в разговоре]** В разговоре предлагался `.gitattributes` с `merge=ours`.
  Он не годится: драйвер `ours` надо прописывать в конфиге каждого клона, и он не срабатывает на конфликтах
  «изменено у них / удалено у нас», а форк как раз удаляет апстримовские workflows и переводы.
- Проверка готовности (критерий 6): прогнать скрипт против текущего `upstream/main` на одноразовой ветке.
