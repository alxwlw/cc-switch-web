# Web parity after the v4.0.35 sync — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Plane:** DX-213

**Goal:** Every frontend `invoke("<command>")` that the v4.0.35 upstream sync added either works in the web console through an `/api/*` route or is listed as desktop-only and hidden in the web UI, and a test fails when a future sync adds an unhandled command.

**Architecture:** The web build aliases `@tauri-apps/api/core` to `web-shims/core`, whose `invoke` is `src/lib/api/adapter.ts`: `mapCommand()` turns a command into an HTTP call to the Axum router in `src-tauri/src/web_api.rs`, and anything unmapped throws `WebUnsupportedError` (`src/lib/api/adapter.ts:1603`). Each task adds the routes for one feature area, backed by the same Tauri-free `*_inner` / service functions the desktop commands call, plus the adapter mappings and their tests. A coverage guard (Task 1) enumerates the commands and pins the desktop-only set.

**Tech Stack:** Rust (Axum, tokio, rusqlite) in `src-tauri`, TypeScript + React + vitest in `src/` and `tests/`.

**Spec:** Plane DX-213 (description and the 2026-11-20 code-check comment). The scope is the 37 commands that `de0a235a..6da70837` (v4.0.35) added and that `src/lib/api/adapter.ts` does not map.

## Global Constraints

- All texts in the repo (code comments, test names, commit messages, docs) are in English.
- No deployment or host details in committed files.
- Routes follow the existing envelope: success `{ "ok": true, "data": … }`, failure `{ "ok": false, "error": … }`; the adapter unwraps it.
- A web route never calls a function that takes `tauri::AppHandle`, a window, or `State<AppState>`; it calls the Tauri-free function the command wraps, extracting one first where the command has none.
- Desktop-only actions (open another app, reveal in a file manager, terminal, app auto-update) are not routed. They go into the guard's desktop-only list, and the UI that triggers them is hidden when `isWeb`.
- `get_auto_update_status` and `download_app_update` stay desktop-only: the web build has its own self-update (`src/lib/api/selfUpdate.ts`).
- Web routes that were removed together with upstream features (circuit breaker, env restore, usage data-sources, provider limits, mcp validate, endpoint last-used, GET universal provider) are not restored.
- Package manager: `npx -y pnpm@10.12.3`. Targeted frontend runs: `npx vitest run <paths>`. Backend tests: `bash scripts/verify-check.sh backend test` (sets umask 022, drops `~/.bun/bin` from PATH).

## Review Focus

- A web user signs in to a Claude account from a browser on another machine: the server must not start `claude auth login` in browser-opening mode on the server host, and the login finishes through the pasted landing URL or code (Task 2 pins `web_login_method`).
- A skill repo token goes in through the web route and never comes back out: no response of the token routes carries the token value (Task 7 pins it).
- The browser drops an MCP connectivity stream half-way (tab closed, navigation) or cancels a batch the server already finished: the server stops the batch and cancel answers `ok` (Task 8 pins both).
- Session content search runs before the index exists, or with an empty query: the route answers an empty result, not an error (Task 6 pins it).
- A quota is asked for an account id the server does not know (Claude, WorkBuddy) or while WorkBuddy is not running on the server: the route answers `{ok:false,error}` with the service's message, the server does not panic (Tasks 2 and 3 pin it).
